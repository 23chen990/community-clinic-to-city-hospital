## 0. 如何使用本文件

### 0.1 权威关系

本文件固定命名为 `Docs/SSOT/CURRENT.md`，是唯一允许直接编辑的产品、玩法和玩家可观察行为真源。

- `Docs/SSOT/Archive/` 中的旧版 DOCX、旧版 Markdown、聊天导出与调研材料仅作历史参考，不得覆盖本文件。
- `Docs/UX/` 中的 APPROVED 图片定义视觉参考；当前可点击 HTML 定义交互参考。
- 代码、配置、测试、原型都必须从属于本文件，不得反向把现有实现当作产品规则。
- SSOT、已批准视觉与已批准交互发生冲突时，停止实现并提交变更记录，不得自行选择答案。
- 未定义的玩家可观察行为不得由开发者或 AI 静默补充。

本版本开始，废止为 Word 服务的 `CURRENT.txt`、`CURRENT.generated.txt` 和手工 SHA 指针流程。发布构建仍需记录 Git commit、内容配置哈希与存档 Schema 版本。

### 0.2 规范标记

| 标记 | 含义 | 实现规则 |
|---|---|---|
| `MUST / 必须` | 当前版本不可违背 | 不满足即阻断实现或验收 |
| `SHOULD / 应当` | 默认方案 | 偏离需 ADR 或 CR，并说明理由 |
| `MAY / 可以` | 允许的实现选择 | 不得误读为必做范围 |
| `LOCKED` | 已批准并进入当前基线 | 只能通过 CR 修改 |
| `EXPERIMENT` | 有基线、范围和验收指标的实验 | 失败时回退基线，不得形成第二套默认值 |
| `DEFERRED` | 当前纵切不实现 | 可保留接口，不得偷偷进入范围 |
| `REFERENCE` | 设计理由、调研或示例 | 不覆盖 LOCKED 规则 |

### 0.3 冲突优先级

发生冲突时按以下顺序处理：

1. 本文件中明确标记为 `LOCKED` 的最新决策；
2. 当前纵切的验收标准与状态机契约；
3. APPROVED 的交互行为；
4. APPROVED 的视觉参考；
5. 配置与测试；
6. 解释性示例、旧版文档和外部研究。

### 0.4 本次重构的关键变化

v0.4 将原 120 余页策划案重构为面向 AI 协作与纵切开发的单一 Markdown 真源，并同步锁定以下最新决策：

- 横屏平板是最佳体验；手机横屏采用自适应简化 UI，但核心玩法、数值与操作完整保留。
- 覆盖 iPad、iPhone、Android 手机与平板；发行基线为海外 App Store / Google Play。
- 免费进入；轻 IAA + 去广告 IAP + 内容扩展包；第一版不做订阅。
- 采用“视觉先行、逻辑纵切、小步验收”，只有 `APPROVED` 的视觉和交互才能实现。
- 首个纵切围绕同一名或同一批患者从进入诊所到班次结算的完整经营场景，不按页面逐个开发。
- 今日目标和事件轨道是叠在地图上的可折叠浮层，不固定占用地图宽度。
- 患者摘要只在点击患者后出现；同一时间只显示一个主要上下文面板。
- 手机横屏复杂面板保持地图在底层，约占屏幕 70%-80%，不默认全屏。
- 化验室用采样、分析、结果发布的队列与资源状态让玩家自行判断瓶颈，不用解释性长文给答案。
- 化验列表称为“排队患者”，不预设“关键患者”。
- 调度执行后的反馈通过地图、队列、患者与人员状态变化表达，不新增独立“调度反馈页面”。
- 班次结算只呈现医院状态与科室状态，不重复堆叠相同指标，不显示教学提示条。
- 社区诊所与社区医疗中心只运行白班和必要收尾；正式白班/晚班双班制在社区医院阶段解锁。内容扩展包可以增加夜间病例、事件与制度，但不绕过医院阶段解锁基础夜班。

# 1. 产品定义

## 1.1 一句话

一款以横屏平板为最佳体验、手机横屏采用自适应简化 UI 的轻量医院流程经营模拟：玩家从一间社区诊所开始，在不完整诊断、有限预算、员工疲劳和突发需求中扩建同一座医院，最终承担城市级医疗责任。

## 1.2 核心幻想

玩家最核心的满足感不是不断点击升级，而是：

> 看懂一家医院为什么混乱，并通过自己的判断、调度、制度和扩建，让它重新顺畅。

体验由三种满足感组成：

- **增长感**：同一家医院的房间、科室、设备、员工和服务范围持续扩大。
- **理解感**：玩家逐渐学会从队列、证据、人员、工位、成本和下游影响中找到真正瓶颈。
- **掌控感**：医院从接近失控恢复到稳定，结果可以追溯到玩家的选择。

## 1.3 核心体验公式

```text
不完整信息
× 有限资源
× 同时发生的患者需求
× 可见且可解释的后果
× 玩家可制定的制度
= 忙、急、但可控的医院经营体验
```

“忙”来自并发和相互依赖，不来自要求玩家不停点金币。  
“急”来自临床风险、患者耐心、人员疲劳和班次时间同时推进，不来自突然弹出的广告倒计时。  
“可控”来自暂停、倍速、优先级、临时调度、长期扩建和自动化制度。

## 1.4 核心差异

1. **患者不是产钱单位**：每名患者拥有不完整证据、风险、耐心、服务路径和可能的长期后果。
2. **科室不是收益皮肤**：新科室必须改变旧患者路径、占用新资源，并制造新瓶颈。
3. **普通工作自动，异常找玩家**：医院变大后，玩家从逐个处理转向制定制度和解决例外。
4. **失败必须可复盘**：等待、离院、转院、返诊和损失都能追到上游原因。
5. **同一家医院有历史**：不通过换城市或换医院重置早期建设、员工成长和制度。
6. **地图就是仪表盘**：队列、负荷、风险、人员覆盖和调度结果优先在地图中表现。
7. **流畅表现是玩法组成**：队列补位、状态恶化、资源占用和部门联动必须连续可读。

## 1.5 P0 硬规范

UI、角色移动、队列变化和经营反馈必须稳定、连续、即时且可读。宁可减少粒子、阴影、角色细节和同屏动画数量，也不能出现：

- 输入迟钝或丢失；
- 队列瞬移、重叠或逆向穿越；
- 帧时间周期性抖动；
- 动画阻塞操作；
- UI 与权威状态不一致；
- 关键问题只能在深层报表中发现。

## 1.6 医疗内容边界

疾病、症状、检查和处置均为游戏化抽象，不构成医疗建议。不得提供真实药品剂量、急救步骤、手术步骤或可用于自我诊断的专业结论。高风险病例的常见安全路径是稳定化与转院，而不是教学现实操作。

## 1.7 原创性边界

可以研究现实医院的一般流程，以及《Project Hospital》等作品中关于队列、容量、人员同步、患者流和可解释系统的抽象原理；禁止复制其 UI、图标、美术、地图、科室顺序、病例表、数值、文本、任务、代码或资产。

# 2. 平台、发行与商业化

## 2.1 平台与设备

| 项目 | LOCKED 决策 |
|---|---|
| 最佳体验 | 横屏平板 |
| 手机形态 | 手机横屏，自适应简化 UI |
| 设备 | iPad、iPhone、Android 手机、Android 平板 |
| 发行 | 海外 App Store / Google Play |
| 输入 | 触控优先；键鼠仅用于开发调试 |
| 离线 | 核心经营循环离线可玩 |

平板的优势是信息并置，而不是拥有手机没有的核心能力。任何必要观察、判断和操作都必须能在手机横屏完成。

## 2.2 商业化

| 项目 | LOCKED 决策 |
|---|---|
| 进入方式 | 免费进入 |
| 广告 | 轻 IAA；只在自然断点或玩家主动触发的临时援助中出现 |
| IAP | 永久去广告 + 内容扩展包 |
| 订阅 | 第一版不做 |
| 核心公平性 | 不付费、不看广告也能完成基础版本完整核心经营循环 |

### 2.2.1 广告边界

- 不在营业过程强插插屏。
- 不在红色危机、患者稳定化、调度确认或结算因果阅读中打断。
- 不把严重患者后果变成广告勒索。
- 临时援助只填补短期缺口，不能代替永久人员、最低科室配置或长期扩建。
- 可能的援助包括临时护士/技师、外送检查加速、少量紧急耗材和远程建议；具体入口为 `EXPERIMENT`。

### 2.2.2 去广告 IAP

永久移除强制插屏。自愿激励援助可保留，或替换为每日有限免费次数。去广告不得改变医院能力、病例难度、质量、收入或进度。

### 2.2.3 内容扩展包

扩展包必须提供真正的新规则、部门、患者结构、城市区域或剧情章节。不得把基础版本应有内容拆成小包售卖。

夜间内容扩展包可以增加夜间病例、员工特质、城市事件、制度和挑战，但基础夜班仍需医院达到社区医院阶段后解锁；付费不直接绕过阶段资质。

# 3. 开发方法与验收门

## 3.1 总体方法

项目采用：

> **视觉先行、逻辑纵切、小步验收。**

页面可以分别设计，但开发必须围绕一条可从头玩到尾的完整经营场景。禁止先把主界面、财务页、建造页和员工页分别做得很漂亮，却没有形成真正可玩的医院循环。

## 3.2 页面状态

| 状态 | 含义 | 是否可进入开发 |
|---|---|---|
| `CONCEPT` | 美术、信息分区和核心氛围探索 | 否 |
| `UX REVIEW` | 元素、入口、层级、异常状态和操作顺序审阅 | 否 |
| `APPROVED` | 产品负责人确认视觉与交互 | 是 |
| `IMPLEMENTED` | 已按批准行为实现并通过验收 | 已完成 |

这些状态是外部审阅标记，不属于正式游戏 UI。

## 3.3 审核流程

1. **概念效果图**：确认美术风格、信息分区和横屏平板感觉。
2. **低保真线框**：确认元素、入口、层级、折叠、异常状态与手机简化方式。
3. **可点击 HTML**：确认点击顺序、弹窗、抽屉、切换、收起和反馈是否直观。
4. **Unity 灰盒**：验证患者移动、排队、倍速、拥堵反馈、触控、动画与真实可玩性。
5. **正式实现**：灰盒通过后才接入完整逻辑、美术、动画和内容。

## 3.4 产品负责人只需判断四件事

- 能否一眼看懂问题；
- 是否产生操作欲望；
- 操作是否符合直觉；
- 操作后是否有清晰反馈。

产品负责人不以读懂代码 diff 为审批前提。完整 diff 留作工程审计；产品审批基于可玩版本、自动测试、风险摘要和可回滚性。

## 3.5 AI 与 Bridge 的职责

- ChatGPT 网页端：整理产品目标、验收条件、视觉与交互方案。
- Engineering Bridge：限定工作区、转交任务、维护受控补丁流程。
- Codex：读取真实项目、实现、测试和生成工程结果。
- 产品负责人：体验原型和测试版本，判断是否满足预期。

`APPROVED` 之前不调用 Codex 做正式实现；尽量一次发送完整纵切任务，减少重复读仓库与返工。

# 4. 同一家医院的长期成长

## 4.1 成长阶段

| 阶段 | 资质 | 核心能力 | 班次规则 | 玩家身份 |
|---|---|---|---|---|
| 0 | 社区诊所 | 接待、全科、治疗、药房 | 白班 + 必要收尾 | 亲自接诊与基础经营 |
| 1 | 社区医疗中心 | 基础化验、X 光、制度、急诊观察雏形 | 白班 + 一次延长收尾；不开放正式夜班 | 负责人 |
| 2 | 社区医院 | 基础住院、全天覆盖 | 解锁正式白班/晚班双班制 | 运营管理者 |
| 3 | 区域医疗中心 | 专科、手术、中央供应、救护车 | 双班与跨班任务成熟 | 部门协调者 |
| 4 | 城市综合医院 | ICU、创伤、感染控制、城市合同 | 24 小时能力与城市应急责任 | 院长 |
| 5 | 教学研究医院 | 培训、研究、病例复盘 | 人才与制度驱动 | 制度设计者 |

## 4.2 夜班规则

- 当前首个纵切与社区医疗中心阶段不开放正式夜班。
- 白班结束后，早期结算主按钮为“安排下一日”。
- 只有医院升级到社区医院或更高资质后，白班结束才可能显示“开始晚班”。
- 夜班解锁后才引入：夜班工资溢价、关键技能覆盖、跨班交接、夜间患者结构和夜间制度。
- 当前阶段可以有最多一次 300 Tick 的延长收尾，但不再接收普通新患者；延长收尾不是夜班。

## 4.3 需求先于解锁

重要科室出现前，玩家必须先经历缺少能力的真实后果。故事顺序应为：

```text
城市或社区需求变化
→ 患者结构变化
→ 现有流程出现可见问题
→ 玩家尝试临时措施
→ 长期扩建成为有意义的选择
→ 新科室解决旧问题并制造新责任
```

## 4.4 3-2-1 科室标准

每个新科室必须：

- 至少影响 3 个已有系统；
- 至少带来 2 种有长期权衡的玩家决策；
- 至少制造 1 个可识别的新瓶颈。

不满足该标准的内容应作为病例、工位升级或旧科室变体，而不是独立科室。

## 4.5 一利一弊升级

阶段 1 中期以后，重要升级必须同时展示收益和新压力。例如：

- 增加候诊座位可减少无座离开，但可能掩盖产能不足并吸引更多患者；
- 增加化验设备可提升分析速度，但不一定解决结果发布的人力瓶颈；
- 延长营业可增加服务量，但会增加疲劳和关键岗位覆盖风险。

# 5. 班次循环

## 5.1 班次结构

| 阶段 | 基线 | 玩家任务 | 结束条件 |
|---|---:|---|---|
| 开诊准备 | 目标 ≤45 秒，无硬超时 | 排班、开放科室、检查库存、选择制度 | 玩家确认开诊 |
| 白班营业 | 3600 Tick / 6 分钟 @1x | 观察、暂停、调度、处理异常 | Tick 3600 |
| 在院收尾 | 0-600 Tick | 处理已在院患者、转院、取消非必要任务 | 无活动对象或达到硬上限 |
| 班次结算 | 目标 ≤45 秒 | 查看医院状态、科室状态并安排下一日 | 玩家确认 |

## 5.2 时间控制

`LOCKED` 速度档：暂停、0.5x、1x、2x。3x 为 `DEFERRED`。

- 暂停是独立按钮。
- 倍速是一个可点击切换或打开选项的按钮，不是静态标签。
- 红色危机到达时，如果当前速度高于 0.5x，默认自动降到 0.5x，但不自动暂停、不抢镜头；玩家可立即恢复。
- 暂停不推进权威 Tick，但允许阅读、调整队列优先级和查看详情。

## 5.3 营业节奏

```text
0%-20%   平静进入
20%-50%  负荷累积与黄色趋势
50%-75%  一个主要压力点
75%-90%  玩家措施开始生效
90%-100% 收尾与未解决问题
```

同一时间最多一个主要红色危机。事件导演不得叠加多个高优先级问题来制造不可理解的混乱。

## 5.4 收尾边界

- Tick 3000：停止生成 Routine/Low 普通步入患者。
- Tick 3300：停止非紧急故事到达。
- Tick 3600：营业结束，进入 Closing 或直接结算。
- Closing 最多 600 Tick。
- 若 Closing 结束仍有 High/Critical 患者，可依据 P10 延长 300 Tick 一次；不接收新患者。
- 结算、日期推进和存档各执行一次，必须幂等。
- 收尾达到硬上限时，尚未完成诊疗的普通、状态稳定患者按 §5.6 离院；High/Critical 患者走明确的安全处置或转院路径，不进入随机次日回流。

## 5.5 软失败

主线默认允许带着后果继续。普通失败表现为收入下降、患者离开、声誉受损、故事目标延后或资质审核延期；不因一次错误频繁重开。

## 5.6 未完成诊疗与次日回流

以下规则由产品负责人于 2026-10-08 确认，属于 `LOCKED`：

- 普通、状态稳定的患者在收尾硬上限仍未完成诊疗时，记录为“未完成诊疗离院”，不算治愈出院，也不确认完整诊疗收入。
- 患者可能下一营业日回来，也可能流失或选择其他医院。等待越久、耐心越低，回来的可能性越低；已完成检查会增加延续诊疗的倾向。具体概率为可回退的 `EXPERIMENT` 参数。
- 当晚只呈现实际发生的未完成诊疗离院；不提前向玩家透露某名患者一定会回来，也不把“未回来”当作已知的“去了其他医院”。
- 次日回来的患者保留身份、已获得的检查结果和诊疗进度，接续尚未完成的步骤；不重复已经完成的登记、初诊、采样、分析或治疗。中断任务已完成的工作量保留，但离院时释放本院资源。
- 外送已发生的费用保留；同一样本不因次日回流重复外送或重复收费。完整诊疗完成后只确认一次收入。
- 回流患者与当日新患者共同使用既有队列和资源，结算分别统计未完成诊疗离院、再次到院、出院与转院，收入和接诊数不重复跨班累计。
- High/Critical 患者不能以随机流失或“明天再来”结束，其路径仍是继续安全处置或转院。
- 当前阶段只安排下一营业日回流。“晚班再来”必须等待正式夜班解锁，不以回流机制提前开放夜班。

产品负责人同时授权对未定义的病例权重、外送费用与时长、疲劳影响及回流概率进行可回退的实验配置与仿真调优；不得因此改变其他已锁定玩法或扩大到暂缓范围。

# 6. 当前首个功能纵切

## 6.1 目标

用最少内容证明：

1. 玩家能否看懂医院为什么堵；
2. 玩家是否愿意通过调度主动解决；
3. 调度后是否能从地图和队列中看到可解释的变化；
4. 患者是否能完成从到达到离院的完整流程；
5. 班次结算是否能帮助玩家理解医院与科室状态。

## 6.2 完整流程

```text
患者进入诊所
→ 接待登记
→ 分诊
→ 全科医生初诊

→ 确诊
→ 药房或治疗室处理
→ 患者结账离院

```

## 6.3 当前固定地图

首切片使用固定社区诊所地图，包含：

- 接待与分诊；
- 全科门诊；
- 基础化验室；
- 治疗室；
- 药房；
- 候诊区；

1. 主运营地图；
2. 患者详情侧栏/浮层；

## 6.6 M1 逻辑验收

M1 必须用纯 C# 自动验证：

- 患者可从进入走到离院；
- 诊断信心不足会产生基础化验申请；
- 化验包含采样、分析、结果发布三段；
- 结果发布可成为独立瓶颈；

- 暂停、0.5x、1x、2x 在相同命令 Tick 序列下得到相同最终状态哈希；
- 不存在资源泄漏、孤儿任务、重复收入或死锁。

其中“4 份 → 1 份”“支援 60 秒”“疲劳 +15%”是当前 `EXPERIMENT` 基线，可通过配置调整，但不得改变因果含义。

# 7. 模拟架构

## 7.1 五条流

| 流 | 核心对象 | 典型瓶颈 | 玩家杠杆 |
|---|---|---|---|
| 患者流 | 到达、排队、转科、离院 | 候诊、路线、下游堵塞 | 分诊、优先、限流、扩容 |
| 信息流 | 症状、证据、结果、诊断 | 化验结果积压、证据不足 | 检查阈值、外送、复诊规则 |
| 人员流 | 岗位、任务、疲劳、休息 | 关键技能缺岗、跨科支援 | 排班、调岗、临时支援 |
| 工位/设备流 | 房间、工位、设备、耗材 | 占用、维护、批处理 | 预留、升级、外送 |
| 现金/声誉流 | 收入、成本、质量、需求 | 固定成本、质量下降 | 合同、采购、扩建、限流 |

## 7.2 核心实体

- `Patient`：病例、证据、风险、耐心、路径、状态、结局。
- `Staff`：职业、技能、疲劳、任务、位置、可用时间。
- `Department`：工位、队列、政策、负荷、状态。
- `Station/Resource`：容量、兼容任务、占用、设备与人员要求。
- `Task`：需求、优先级、资源集合、时长、输出和失败原因。
- `Event`：触发条件、压力预算、需求修改和后果。
- `LedgerEntry`：收入、成本、预留、退款与幂等键。

## 7.3 权威 Tick

- 10 Hz 固定 Tick；每 Tick 100 ms @1x。
- 表现帧率、Tween、角色动画和 UI 刷新不得改变模拟结果。
- 权威状态不存 `float/double`；概率、比例、风险和耐心用整数或 basis points。
- 金钱使用 `Int64` 整数最小单位。
- 实体 ID 使用持久化单调 `UInt64`，销毁后不复用。

## 7.4 单 Tick 顺序

1. 受理命令；
2. 推进班次、维护、Buff 与定时状态；
3. 更新风险、耐心和等待；
4. 推进任务；
5. 释放资源；
6. 更新队列与等待老化；
7. 运行 AI 与政策；
8. 原子预约、创建任务和移动；
9. 记账、事件导演和到达计划；
10. 写入领域事件、根因边和统计；
11. 计算状态哈希与快照。

同一任务同一 Tick 最多完成一次；新患者最早在下一 Tick 进入可调度状态。

## 7.5 命令契约

所有玩家操作转为命令：

```text
command_id
submitted_tick
actor_id
command_type
payload
precondition_hash（可选）
```

命令结果为 `Accepted / RejectedInvalid / RejectedStale / RejectedInsufficient / Deferred`。UI 按下后先显示“已提交”，收到权威结果后再显示成功或原因；禁止先改本地状态假装成功。

## 7.6 原子资源预约

多资源任务必须全有或全无：

```text
工位 + 设备 + 关键员工 + 支援员工 + 目的地容量
```

缺少任何必需资源时，不持有其余资源。软预约 TTL 基线 50 Tick，超时释放并至少等待 10 Tick 再重试，避免死锁和抖动。

## 7.7 队列评分

```text
QueueScore = ClinicalBase
           + WaitAge
           + PolicyModifier
           + StoryModifier
           + ContinuityBonus
           - TravelPenalty
```

同分依次按 `enqueue_tick` 更早、`EntityId` 更小排序。等待老化与饥饿保护避免低风险患者永久得不到服务。高风险优先不能无限压制普通患者。

## 7.8 随机与重放

随机算法和分流必须稳定。至少分离：

- PatientArrivalRng；
- CaseTruthRng；
- StaffPoolRng；
- EventDirectorRng；
- CosmeticRng。

视觉随机不得改变权威随机流。同一快照、配置哈希、随机状态和命令日志必须逐 Tick 得到相同状态哈希。

## 7.9 根因追踪

等待、离院、恶化、转院、失败和损失必须记录轻量因果边：

```text
cause_entity
→ effect_entity
→ reason_code
→ start_tick/end_tick
→ magnitude
→ parent_edge
```

结算从记录聚合共同上游，不在班次结束时根据结果猜原因。

# 8. 患者与诊断

## 8.1 四个独立维度

| 维度 | 核心字段 | 玩家可见 |
|---|---|---|
| 临床 | 严重度、风险、恶化、稳定化 | 风险等级、状态动画 |
| 信息 | 候选、证据、诊断信心 | 症状、候选、信心 |
| 服务 | 当前科室、队列、路径、阻塞 | 当前步骤、等待原因 |
| 情绪 | 耐心、疼痛、满意度、信任 | 表情、耐心、投诉 |

风险和耐心必须分离。低风险患者可能耐心很低；高风险患者也可能很耐心，但仍需优先处理。

## 8.2 患者状态机

```text
Spawned
→ Arriving
→ WaitingTriage
→ WaitingConsult
→ InConsult
→ WaitingExam / InExam / ResultPending
→ WaitingConsult（复诊）
→ WaitingTreatment / InTreatment / Pharmacy
→ Discharge
→ Completed
```

异常分支：

```text
Waiting/InService
→ Emergency / Stabilized / Transfer
→ Completed

Patience = 0 且非危急
→ LeftWithoutCare
→ Completed
```

危急患者不得因耐心归零自行离院，其路径只能是继续救治、稳定后转院或未来扩展终态。

## 8.3 风险与耐心

内部均使用 0-10000 整数。

```text
RiskNext = clamp(
  Risk + BaseDeterioration + WaitModifier + UntreatedModifier - Stabilization,
  0, 10000)

PatienceNext = clamp(
  Patience - BaseLoss - Crowding - Uncertainty + Communication,
  0, 10000)
```

风险层级基线：

| 层级 | 范围 |
|---|---:|
| Routine | 0-999 |
| Low | 1000-3499 |
| Medium | 3500-6499 |
| High | 6500-8499 |
| Critical | 8500-10000 |

稳定化降低风险增长或暂时封顶，不自动增加诊断信心。

## 8.4 诊断信心

病例包含 2-4 个游戏化候选。检查揭示证据并更新支持度：

```text
Support_i = max(0, Prior_i + Σ EvidenceWeight_i)
Confidence = floor(10000 × TopSupport / max(1, Σ Support))
```

医生技能不凭空改变真实病因，而是影响证据发现、误读、检查建议和服务时间。

## 8.5 检查价值

检查的代价不仅是现金，还必须占用时间、人员、设备或工位。

```text
ExamValue = 预期信心提升
          + 高风险候选覆盖
          - 预计等待成本
          - 金钱成本
          - 患者不适/耐心成本
```

普通病例可以自动选择；玩家在异常病例和系统拥堵时介入。

## 8.6 当前切片病例范围

M1 使用 6 个可验证病例模板，优先覆盖：

- 低风险上呼吸道样症状；
- 流感样疾病；
- 咽部感染样症状；
- 轻度过敏样反应；
- 脱水；
- 腹痛高风险分支。

其中至少 3 个病例需要基础化验，至少 1 个病例可在低信心下快速处理但增加返诊风险，至少 1 个病例等待过久会进入高风险或转院路径。

M3 扩展至 15 个病例模板。

# 9. 科室与人员

## 9.1 通用科室协议

每个科室必须声明：

1. 输入；
2. 资源；
3. 处理；
4. 输出；
5. 失败模式；
6. 玩家政策；
7. 依赖关系。

没有隐式科室逻辑。关闭、缺员、设备故障、耗材不足和下游满载都必须有确定的等待、替代、外送、转院或失败路径。

## 9.2 接待与分诊

- 输入：步入患者和事件批次。
- 资源：登记台、接待员、分诊能力、候诊容量。
- 输出：初始风险、路线和队列优先级。
- 失败：入口队列、候诊压力、漏掉高风险标记。
- 当前纵切：登记与分诊可合并为相邻工位，但逻辑状态分开。

## 9.3 全科门诊

- 初诊和结果复诊使用不同队列。
- 结果返回患者应获得连续性加成，避免重新排到所有新诊之后。
- 当前 `EXPERIMENT` 基线：新诊 : 结果复诊 = 2 : 1；高风险复诊立即优先。
- 输出可以是检查申请、治疗计划、处方、观察、离院或转院。

## 9.4 基础化验室

化验室必须表现为三段队列：

| 阶段 | 队列对象 | 核心资源 | UI 数量含义 |
|---|---|---|---|
| 采样 | 患者 | 采样工位 + 可采样员工 | “等待 5 人”代表等待采样的患者人数 |
| 分析 | 样本 | 分析仪批次 + 技师 | “待测 3 份”代表等待或正在排队分析的样本份数 |
| 结果发布 | 结果任务 | 结果审核/发布能力 | “待发 4 份”代表已完成分析但尚未回到医生的结果份数 |

### 9.4.1 UI 证据链

玩家应通过以下信息自行判断瓶颈：

- 队列数量；
- 工位/设备/人员覆盖；
- 处理速度或进度；
- 地图上的等待实体；
- 一个明确但不重复的瓶颈标记。

禁止使用长句直接告诉玩家“因为只有一名技师，所以结果发布堵塞”。如果结果发布是瓶颈，可使用单个感叹号或“瓶颈”标签之一，不能同时重复堆叠；也不能用像选中状态的红色边框误导玩家。

### 9.4.2 排队患者

列表标题统一为“排队患者”。

- 不称“关键患者”或“受影响患者”。
- 不预设某个患者天然更重要。
- 列表显示头像、姓名、风险图标与等待时间。
- 玩家根据风险和等待自行决定是否选择“风险优先”。

## 9.5 临时调度

当前化验拥堵提供三类方案：

| 方案 | 核心作用 | 主要代价 |
|---|---|---|
| 风险优先 | 高风险结果先发布 | 其他普通患者等待增加 |
| 临时支援 | 召回或调入技师 60 秒，清理积压 | 技师疲劳增加，后半班效率可能下降 |
| 外送样本 | 把普通样本交给外部处理，腾出本院容量 | 额外成本与更长返回时间 |

交互结构 `LOCKED`：

- 三个方案横向并列；
- 当前选择使用蓝色边框和勾；
- 方案卡只写短标题，不写解释性副标题替玩家下结论；
- 下方显示所选方案的预计结果；
- 最下方只有一个明确执行按钮；
- 执行前可取消或暂时忽略。

## 9.6 调度执行后的反馈

不新增独立“调度反馈页面”。执行后通过现有经营界面表达：

- 化验结果积压数字下降；
- 结果发布速度恢复；
- 排队患者状态更新；
- 患者返回门诊；
- 地图中的化验室高亮逐步消退；
- 技师疲劳上升；
- 事件轨道记录“临时支援开始/结束”。

反馈动画不得成为权威状态完成的条件。

## 9.7 治疗室与药房

治疗室完成无需住院的基础处置和稳定化；药房完成处方交付和最终离院。二者在当前纵切只需支持与 6 个病例相匹配的抽象治疗类别与库存，不使用真实药名或剂量。

## 9.8 员工与任务 AI

当前职业：接待员、护士、全科医生、化验技师、药房员工。

员工 AI 流程：

```text
过滤合法任务
→ 计算效用
→ 按稳定顺序匹配
→ 短暂承诺任务，避免频繁切换
```

```text
Utility = QueueScore
        + SkillFit
        + RoleFit
        + Continuity
        + Policy
        - FatiguePenalty
        - DistancePenalty
        - SwitchPenalty
```

员工无合法任务时必须显示明确原因：空闲、休息、无兼容任务、等待设备、被政策限制或路径阻塞。

# 10. 财务、医院声誉与结算

## 10.1 玩家主要经营指标

主界面与结算的玩家一级指标统一使用：

- 现金；
- 医院声誉；
- 当前医院负荷；
- 接诊进度或接诊人数；
- 班次日期与时间。

旧版“综合质量”不作为一级主指标。安全、有效性、及时性、体验与连续性仍可作为内部质量维度或二级报表，用于解释医院声誉变化。

## 10.2 收入确认

检查本身产生时间与耗材成本，不直接喷金币。完整诊疗、治疗或合理转院完成时确认收入与质量结果。

财务事件必须幂等；重复回调、重放或恢复最多记账一次。

## 10.3 班次结算页面

结算页进入时模拟已停止。页面不显示暂停与倍速，不显示教学提示条。

### 医院状态

- 员工状态；
- 医院声誉；
- 接诊；
- 出院；
- 转院；
- 治疗中；
- 本班收入。

同一指标只出现一次，不在顶部、大卡片和医院状态中重复三遍。

### 科室状态

每个科室用短状态表达当前忙闲或本班结果，例如：

- 接待与分诊：平稳；
- 全科门诊：繁忙；
- 基础化验室：已缓解；
- 治疗室：平稳；
- 药房：平稳；
- 候诊区：略拥挤。

点击科室卡可以查看本班详情，例如最高积压、支援时长、班末积压和人员疲劳；主结算页不常驻长篇根因报告。

### 主按钮

- 夜班未解锁：`安排下一日`；
- 夜班已解锁且白班结束：`开始晚班`；
- 晚班结束：`结束本日`。

当前纵切固定显示“安排下一日”。

# 11. UI 与交互

## 11.1 总原则

- 不用长篇说明替玩家得出结论。
- 用队列、人员、工位、积压、速度和地图状态形成证据链。
- 所有浮层、分组和详情面板都有清楚的展开/收起状态。
- 同一时间只显示一个主要上下文面板。
- 地图不能因为左侧卡片展开而缩小或重新排版。
- 卡片按内容自适应，不强制所有卡片同高。
- 所有重要操作先显示预计影响，再由玩家确认。
- 不出现地图行走箭头；路径只在玩家主动查看某个对象时以临时覆盖层显示。

## 11.2 平板主运营界面

### 顶部

- 第几日、几点钟、白班/晚班；
- 现金；
- 医院声誉；
- 当前医院负荷；
- 接诊进度；
- 独立暂停按钮；
- 可点击倍速按钮；
- 设置。

不显示“游戏时间”这种技术词。

### 地图

中央医院地图占最大面积。房间、患者、员工、队列和局部负荷是主要证据。警报只局部高亮问题科室，不让全屏变红。

### 左侧浮层

“今日目标”和“事件轨道”叠在地图上，不占固定布局宽度。两者独立展开/收起，收起后保留紧凑标题条或图标。

### 右侧上下文

- 未选中对象时不显示患者摘要，地图使用完整空间。
- 点击患者才显示患者摘要；点击“查看病历”进入更深层病历。
- 点击科室或警报切换为科室详情。
- 点击员工切换为员工详情。
- 点击地图空白、关闭或选择其他对象后收起/切换。
- 患者面板与科室面板不并排叠加。

### 底部工具栏

稳定入口：建设、员工、科室、制度、财务、报告。正式 UI 不因活动、礼包或广告改变顺序。

## 11.3 手机横屏

手机不是压缩版平板，而是同一功能的自适应布局：

- 地图仍是底层主视图；
- 今日目标和事件轨道默认折叠为浮动入口；
- 顶部减少同时常驻指标；
- 底部只保留高频入口，低频入口进入“更多”；
- 患者详情可使用底部或右侧浮层；
- 化验拥堵等复杂面板约占屏幕宽高的 70%-80%，地图仍可在周围或底层看到；
- 复杂面板不是默认全屏，也不能把地图重新排版或压缩；
- 面板可收起为边缘小标签，再次点击恢复；
- 班次结算是独立页面，可以占满主要内容区域。

## 11.4 卡片尺寸

平板和手机的面板高度由内容决定。上下文卡支持紧凑、标准和扩展三档，或通过内容区滚动。禁止为了统一卡片高度留下大片空白。

## 11.5 警报与注意力预算

| 级别 | 表现 | 规则 |
|---|---|---|
| 黄色趋势 | 静态图标、轻提示 | 可稍后处理 |
| 橙色风险 | 局部脉冲、预计时间 | 即将产生损失 |
| 红色危机 | 唯一主注意动画、自动降速 | 立即决定或明确忽略 |
| 信息 | 短暂数字/图标 | 不占事件轨道 |

同一时刻最多一个主要红色动画和一个次要橙色提醒。广告、奖励、商店和活动不得使用相同的危机视觉语言。

## 11.6 触控与可访问性

- 常规触控目标至少约 48dp 等效；
- 风险不只靠颜色，同时使用图标、形状和文字；
- 支持 UI 缩放和减少动态效果；
- 所有自动镜头移动可被拖动、缩放或点击取消；
- 面板滑入时地图仍可暂停和缩放；
- Back/Esc 顺序：关闭阻塞模态 → 上下文菜单 → 抽屉/面板 → 清除选择 → 暂停菜单。

# 12. 动画与性能

## 12.1 目标

| 指标 | LOCKED 目标 |
|---|---|
| 帧率 | 稳定 60 FPS；必要时稳定回退 30 FPS |
| 帧时间 | P95 ≤16.7ms；P99 ≤25ms |
| 模拟 Tick | 平均 ≤2ms；P99 ≤4ms |
| 输入反馈 | 物理按下到视觉反馈 ≤100ms |
| 活动逻辑实体 | 垂直切片上限 120 |
| 可见移动角色 | 上限 80，超出只降表现 |
| 稳态分配 | 权威 Tick、队列选择和 AI 规划 0 B GC |

## 12.2 动画规则

- 动画只消费领域事件，不反写权威状态。
- 队列重排必须先确定权威目标，再平滑补位。
- 连续同类事件可以合并表现，但不能丢状态或 ReasonCode。
- 动画可跳过、取消或重定向；动画完成回调不能完成任务、扣款或改变风险。
- 调度反馈不新增独立页面，而是由队列、患者、员工和地图状态连续变化表达。

## 12.3 推荐动效时长

| 动效 | 建议 |
|---|---:|
| 按钮按下 | 80-150ms |
| 面板滑入/折叠 | 180-260ms |
| 队列补位 | 220-450ms |
| 状态颜色过渡 | 250-500ms |
| 镜头聚焦 | 250-450ms，可立即取消 |
| 危机脉冲 | 1.2-1.8s 循环，同屏一个 |

## 12.4 性能降级顺序

1. 减少粒子、装饰性阴影和高成本后处理；
2. 降低非选中角色的闲置动画与表情刷新；
3. 降低屏外表现更新；
4. 切换 30 FPS 和较低渲染分辨率。

绝不通过减少患者、暂停风险、改变服务时间或修改队列结果来换取帧率。

# 14. 测试与完成定义

## 14.1 M1 自动测试

必须至少覆盖：

- 患者状态机正常路径、取消路径、转院路径；
- 风险和耐心逐 Tick 更新；
- 化验三段队列；
- 原子资源预约与超时释放；
- 结果发布瓶颈；
- 临时支援、疲劳和积压变化；
- 新诊/复诊队列；
- 记账幂等；
- 暂停与多倍速确定性；
- 固定种子重放；
- 无死锁、负资源、孤儿任务或重复收入。

## 14.2 M1 退出门槛

- 可批量运行至少 100 个班次；
- 0 死锁；
- 0 资源泄漏；
- 0 重复记账；
- 预设的化验积压、人员不足和复诊回流根因都能被正确记录；
- 同种子同命令日志得到一致哈希；
- Simulation 可在无 Unity Editor 的 .NET 测试进程中构建和运行。

## 14.3 M2 Unity 灰盒验收

测试者无需外部说明即可：

- 看懂患者从接待到离院的主流程；
- 发现化验室发生拥堵；
- 通过采样、分析、结果发布的 UI 证据指出正确瓶颈；
- 理解三种调度方案的收益与代价；
- 执行方案后从地图和队列看到变化；
- 在平板与手机横屏完成相同核心操作；
- 在高峰场景中暂停、切倍速、选择对象和关闭面板，无明显输入迟钝。

## 14.4 UI 完成定义

- 默认、加载、空、错误、折叠、展开、选中、未选中状态完整；
- 同时最多一个主要上下文面板；
- 所有按钮有即时反馈与权威结果状态；
- 手机复杂面板保留地图底层；
- 不出现独立调度反馈页；
- 不出现“关键患者”预设；
- 不用长解释替玩家判断；
- 减少动态效果和 UI 缩放可用。

## 14.5 缺陷等级

- `S0 Blocker`：存档损坏、重复扣款/奖励、确定性分叉、无法启动、隐私/法律风险。
- `S1 Critical`：患者/资源卡死、纵切无法完成、持续崩溃、严重帧时超标。
- `S2 Major`：根因错误、主要 UI 不可读、输入冲突、有绕过路径的系统错误。
- `S3 Minor`：非阻塞表现、文本和小范围布局问题。

M1/M2 不允许存在 S0/S1；S2 必须有 Owner 和明确处理计划。

# 16. 当前批准的 UX 行为清单

以下行为已进入当前基线，除非 CR 修改，不应由 Codex 重新设计。

## 16.1 主运营地图

- 横屏平板视觉方向已批准。
- 默认不显示患者摘要。
- 点击患者后才显示患者摘要和“查看病历”。
- 日期、时刻和“白班/晚班”显示在左上；不使用“上午班次”。
- 暂停与倍速是两个独立按钮；倍速按钮可切换。
- 今日目标和事件轨道为地图浮层，可展开/收起。
- 左侧浮层展开不挤压地图。
- 底部导航固定。
- 地图不显示行走箭头。

## 16.2 化验拥堵

- 点击警报或化验室打开右侧/浮动上下文面板。
- 化验室局部高亮，不让全屏变红。
- 展示采样、分析、结果发布三段及其队列数量。
- 数量明确区分“人”和“份”。
- 只保留一个瓶颈标识，不同时使用多个感叹号、红框和“瓶颈”标签。
- 红色表示压力，不做像选中卡片一样的边框。
- 列表标题为“排队患者”。
- 三个调度方案横向比较；选中为蓝色。
- 方案卡不写多余解释副标题。
- 下方显示预计结果与代价；点击执行后返回经营状态持续观察。

## 16.3 手机横屏

- 不是把平板整体缩小。
- 地图仍在底层。
- 复杂面板约占屏幕 70%-80%，不默认全屏。
- 面板可收起、恢复和关闭。
- 卡片按内容自适应，避免大片空白。
- 班次结算可以独立显示。

## 16.4 班次结算

- 显示医院状态和科室状态。
- 医院状态包含：员工状态、医院声誉、接诊、出院、转院、治疗中、本班收入。
- 科室状态显示各科室忙闲或“已缓解”等结论。
- 不重复展示同一组统计。
- 不显示“点击科室卡可查看……”之类教学提示。
- 不显示暂停和倍速。
- 当前阶段主按钮为“安排下一日”。
