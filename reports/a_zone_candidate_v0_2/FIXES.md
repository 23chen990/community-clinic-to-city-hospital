## 1. 测试是怎么加载配置的（回应"不能只在测试脚本里补默认值"）

`tests/harness.js` 的做法：

1. 读入**真实** `index.html`，用 jsdom 建立真实 DOM；
2. 在 jsdom 自己的 JS 上下文里，按 `<script>` 顺序依次执行**真实** `config.js` → `game.js`；
3. 只补浏览器表面：canvas 2D 桩、可控 rAF、可控时钟、可控 localStorage、逻辑视口。

**驱动不注入任何游戏配置默认值。** 配置缺字段就是缺字段。

这一点由回归项 `R13` 反向证明：把 `prototype/config.js` 里的
`arrival_jitter_low` / `arrival_jitter_high` 删掉后重新加载，
`start()` **拒绝启动**、`State.bootError` 列出这两个字段、页面显示明确错误页
（`R13.1`–`R13.4`）。也就是说，修复前那 47 条失败观察不是脚本造成的假象。

另外 `R0.5` 断言页面加载后的配置里 15 个必需字段全部存在——
如果哪天有人再删字段，这一条会先红。

## 2. 第一优先级

### P0-1 · 首位患者之后彻底断流

**失败复现**（`origin_frozen`，日志 `logs/pre_fix_repro.log`）

| 断言 | 观察 |
|---|---|
| `F0.1` / `F0.2` | 页面加载后的 `IN` 里没有 `arrival_jitter_low` / `arrival_jitter_high` |
| `F0.3` | `jitter()` 返回 `NaN` |
| `F1a.1`–`F1a.4` | 3000 tick 后：完成 **1** 人、金币 **435**、在院 **0**、`lastArrivalTick` 为 **NaN** |
| `F1b.*` | 延长到 18000 tick 仍然完成 1 人（不是暂态） |
| `F1.c` | 断流确认 |

**根因**：`game.js` 的 `jitter()` 读 `IN.arrival_jitter_low/high`，配置里没有这两个键
→ `NaN` → `State.lastArrivalTick -= Math.round(ARRIVAL_INTERVAL * (NaN - 1))` → `lastArrivalTick` 变 `NaN`
→ 到院条件 `simTick - NaN >= ARRIVAL_INTERVAL` 永远为 `false` → 首位患者之后再无到院。

这条路之所以能一路走到线上，是因为**缺字段没有任何校验**，静默变成 `NaN`。

**修正**（`config.js` + `game.js`）

1. `config.js` 补齐 `arrival_jitter_low: 0.7` / `arrival_jitter_high: 1.3`（与验收方 D 组诊断通道所用的一致）。
2. `game.js` 新增 `validateConfig()`：15 个必需数值字段逐一校验，缺失/非有限值/区间倒置都在启动时列出。
   校验不通过 → 不启动、显示错误页、`console.error`。**不再以空白或 NaN 假装正常。**
3. 到院调度改为显式 `State.nextArrivalTick`，不再回改 `lastArrivalTick`；
   `jitter()` 在输入非有限时返回 `1` 兜底；`arrivePatients()` 每次都会检查并修复非有限的 `nextArrivalTick`。

**回归**（日志 `logs/post_fix_regression.log`）

- `R0.5` 15 个必需字段齐全；
- `R1.1` `nextArrivalTick` 始终有限；
- `R1.2` 3000 tick（5 模拟分钟）完成 **17** 人（>1）；
- `R1.3` 6000 tick 继续增长；
- `R1.4` 18000 tick（30 模拟分钟）完成 **117** 人，未断流；
- `R1.5` 累计到院 **119** 人，与「4 人/分钟 × 30 分钟 ≈ 120」同量级；
- `R13.1`–`R13.5` 缺字段拒绝启动 + 完整配置可启动。

### P0-2 · 开放科室时重复发放开业补助

**失败复现**

- `F2.1` 首例完成后金币 **435**（250 + 首例 35 + T01 150）；
- `F2.2` 开放 TR 后 **185**（只应扣 400）；
- `F2.4`/`F2.6` T02 后 **285**，正确口径应为 **135**，即**多发了 150**；
- `F2.7` 再开放 LB 又叠加一次 150（2000 − 1400 + 150 = 750）。

**根因**：`doAction()` 的 `unlock` 分支里对 `TR`/`LB` 无条件追加 `IN.opening_grant`。
`opening_grant` 与 `T01` 奖励同为 150，是同一笔一次性开业补助被实现了两遍。

**修正**

- 删除 `unlock` 分支里的补助发放，`T01`「完成第一位患者的服务」成为**唯一**口径；
- `config.js` 里给 `opening_grant` 加注释说明它是 T01 的同一笔，不得在开放科室时重复发放；
- `tasks[]` 增加 `oneTime: true` 标注；发放时写入 `State.stats.grantLog`（记录 id/金额/时刻），
  让"有没有重复发"变成可断言的证据，而不是靠肉眼看余额。

**修正过程中发现并修掉的第二个问题**：我最初在 `unlock` 分支里顺手加了 `stats.investments++`，
这会让「开放科室」也触发 T04「完成一次提速或扩容」，等于偷偷改了任务口径。
已改回：**开放科室不计入 investments**，并加断言 `R3.7` / `R3.15` 锁住。

**回归**

- `R3.3` 首例完成后 = 250 + 首例奖励 + 150；
- `R3.4` 开放 TR 后 = 首例后 − 400（不再有额外 150）；
- `R3.5` 明确断言"没有多出来的 150"；
- `R3.6` T02 后 = 首例后 − 400 + 100；
- `R3.9`/`R3.10` 补助条目只可能来自 `CFG.tasks` 且每个任务最多一次；
- `R3.11` 明细恒为 `T01:150,T02:100`；
- `R3.12` `opening_grant` 与 T01 奖励同额（同一笔）；
- `R3.13`/`R3.14` 开放 LB 不叠加任何补助；
- `R3.17`/`R3.18` 扩容后 T04 恰好一次，再跑 300 tick 不重复。

### P0-3 · 病例末站倍率没有接入服务时长

**失败复现**

- `F3.5` `serviceTicks()` 签名里没有病例倍率参数；
- `F3.2` C03（GP→PH，末站倍率 1.30）末站实际 **80 tick = 8.0 秒**，应为 **104 tick = 10.4 秒**；
- `F3.4` C06（GP→TR，末站倍率 1.30）末站实际 **200 tick = 20.0 秒**，应为 **260 tick = 26.0 秒**。

**根因**：`serviceTicks(room, level)` 只算 `base_ticks / (1 + level × gain)`，
`CFG.cases[].last_multiplier` 从未被读取。

**修正**

- `serviceTicks(room, level, multiplier)` 增加第三参数，缺省为 1（房间面板仍以基础时长展示）；
- 患者生成时保存 `p.lastMultiplier = cs.last_multiplier`；
- 派工时记录 `p.willBeLastStation = (routeIdx === route.length - 1)`；
- 到位开始服务时按 `末站 ? lastMultiplier : 1` 计算时长。

**回归**

- `R2.C03.3` 各站 tick = `[120, 104]`；
- `R2.C04.3` = `[120, 200]`；`R2.C06.3` = `[120, 260]`（倍率 1.30）；
- `R2.C08.3`（三站病例 GP→LB→PH）= `[120, 160, 96]`——**中间站不吃末站倍率**；
- `R2.C09.3`（GP→LB→TR）= `[120, 160, 220]`；
- `R2.*.4` 倍率 ≠ 1 时末站时长严格不等于基础时长；
- `R2.speed.1/2` 提速 Lv1 后首站 = 104，末站倍率依然生效；
- `R2.cfg.1`–`R2.cfg.4` 倍率为 1/1.3/缺省三种情况下的取值。

## 3. 第二优先级

### P1-1 · 保存失败静默、未知版本被接受、坏档被覆盖

**失败复现**

| 断言 | 观察 |
|---|---|
| `F4.1`/`F4.2` | 注入写入失败后，内存金币 1000 → **750**、TR **已开放** |
| `F4.3` | 存档仍是 **1000**（内存与磁盘不一致） |
| `F4.4` | 界面**没有**任何保存失败提示（toast 报的是"开业补助 +150"） |
| `F4b.1`/`F4b.2` | `v=999` 的快照被 `loadGame()` 接受，12345 金币被直接采用 |
| `F4c.1`–`F4c.3` | 坏档被拒绝后，30 秒自动存档把原文**覆盖**掉，且**没有任何备份** |

**根因**：`saveGame()` 的 `catch` 只吞异常；`doAction()` 先改内存再 `saveGame(true)`（静默），
失败不回滚、不提示；`loadGame()` 不校验版本也不校验数值。

**修正**

1. **事务化玩家命令**：`doAction()` 先做纯校验 → 快照（金币/统计/房间/登记位）→ 改内存 → 立刻写盘。
   写盘失败即**整体回滚**并明确提示「保存失败，本次改动已撤销」。
2. **写回校验**：`setItem` 后立刻 `getItem` 比对，内容不一致（配额静默丢弃）同样判失败。
3. **版本校验**：存档模式 `v` 从 1 升到 **2**；`loadGame()` 拒绝任何非 2 的版本。上传版 v1 存档
   含有 NaN 化的到院字段，属于必须拒绝的旧格式。
4. **结构校验**：`isValidSnapshot()` 检查金币/时刻/速度等数值有限、患者坐标有限、路线非空。
5. **坏档备份**：拒绝载入前先把原文写到 `sunny_hospital_save_v1.bak.<原因>.<时间戳>`，
   之后自动存档不会再把它冲掉。
6. **可见的失败状态**：HUD 新增「存档」状态位（正常/失败），失败时变红；手动保存失败另弹 toast。

**回归**

- `R4.1`–`R4.6` 抛异常式失败：金币回滚、TR 未开放、存档未改写、toast 提示、`saveStatus = failed`、HUD 显示"失败"；
- `R4.7`–`R4.9` 静默丢弃式失败：同样回滚；
- `R4.10`–`R4.13` 正常购买仍成功、落盘内容与内存一致且带版本号；
- `R5.1`–`R5.5` `v=999` 被拒绝（reason=`version`）、金币未采用、原文已备份且内容含 999；
- `R5.6`–`R5.11` 坏档被拒绝（reason=`corrupt`）、原文已备份，**自动存档之后备份依然存在**；
- `R5.12`–`R5.14` 上传版 v1 存档被拒绝，900 金币未被采用；
- `R5.15`–`R5.20` 合法同版本存档可恢复，恢复后 HUD 倍速文案同步为 4×；
- `R5.21`–`R5.26` **进行中**存档（有患者在途）→ 恢复到全新页面：金币/时刻/患者数/工位占用
  完全一致；继续跑 3000 tick 仍满足 `admitted = completed + transferred + 在院`，
  没有坐标变 NaN，`nextArrivalTick` 仍有限（不会因为读档再次断流）。

### P1-2 · 打开房间面板不暂停；大帧间隔补跑

**失败复现**

- `F5b.1`–`F5b.3` 打开面板后 `State.paused` 仍为 `false`，模拟继续推进 100 tick；
- `F5a.1` 合成 60 秒帧间隔 → 每帧被补跑 **200 tick = 20 模拟秒**，3 帧累计 **600 tick**。

**根因**：`openRoomPanel()` 只切 DOM 类名，不碰 `State.paused`；
`loop()` 用 `acc += dt * speed` 且不设 `dt` 上限、不检查页面可见性。

**修正**

- 暂停拆成两个来源：`pausedByUser`（暂停按钮）与 `pausedByPanel`（房间面板）。
  `isPaused()` 为两者之或；`State.paused` 保留为合成只读字段，语义不变。
  打开面板暂停、关闭恢复，且**不会覆盖用户自己按下的暂停**。
- `loop()` 单帧 `dt` 上限 `MAX_FRAME_DT = 0.25` 秒；补跑上限与上限绑定（最多 10 tick），
  超出即丢弃累加器，不累积到下一帧。
- 页面隐藏（`visibilitychange` → `hidden`）时完全停止模拟并清空累加器；
  `pagehide` / `pageshow` 同理；回到前台重置 `lastTime = performance.now()`，**不补跑**。
- 面板打开会导致可用宽度变化，因此在开/关面板时重新 `fitCanvas()`。

**回归**

- `R6.1` 每个 60 秒间隔的帧最多推进 **3** tick（修复前 200）；
- `R6.2` 3 帧累计 < 20 tick（修复前 600）；
- `R6.3` 页面隐藏期间推进 **0** tick；
- `R6.4` 回到前台第一帧推进 ≤ 4 tick（没有补跑积压）；
- `R7.1`–`R7.7` 面板打开即暂停、`State.paused` 合成正确、rAF 循环期间不推进、关闭后恢复；
- `R7.8`–`R7.11` 用户暂停与面板暂停互不覆盖。

### P1-3 · 面板按钮与 HUD 状态不刷新

**失败复现**

- `F6a.1`–`F6a.3` 金币 250 时 GP 提速按钮禁用；金币涨到 435 后**同一个节点仍然禁用**，必须重开面板才可用；
- `F6b.1` 真实速度 4×，按钮仍显示「1×」。

**根因**：`renderRoomPanel()` 只在"打开面板"和"购买成功"时调用；
`updateHUD()` 只管三个数字，不碰按钮文案，也不碰面板按钮可用性。

**修正**

- `renderRoomPanel()` 把三个按钮节点存进 `panelRefs`；
- 新增 `refreshPanelAffordability()`，`updateHUD()` **每帧**调用它，只改 `disabled`、**不重建 DOM**，
  所以不会丢焦点、不会让玩家点到一半的按钮跳走；
- `updateHUD()` 同时同步：暂停按钮文案（跟随 `isPaused()`）、倍速按钮文案（跟随 `State.speed`）、
  存档状态位。

**回归**

- `R8.1`–`R8.7` 金币 250 → 435 → 900 → 100 的双向刷新，并断言**复用同一个 DOM 节点**；
- `R8.8` 倍速文案 = 4×；
- `R8.9`/`R8.10`/`R8.10b`/`R8.10c` 暂停文案与 `isPaused()` 始终一致（不是写死的字符串）；
- `R8.11`/`R8.12` 购买后等级提升且面板显示 `Lv1 → Lv2`。

### P1-4 · 横屏视口面板越界、非等比缩放、文字与患者过小

**失败复现**（真实 Chromium，量化数据见 `logs/browser_evidence.log`）

| 视口 | 面板右侧越界 | 标题实测字号 | 患者实测直径 | 关闭按钮在视口内 | 购买按钮在视口内 |
|---|---:|---:|---:|---|---|
| 1280×720 | **192.0 px** | 19.8 px | 14.4 px | **否** | **否** |
| 844×390 | **41.0 px** | **9.7 px** | **7.1 px** | **否** | **否** |
| 667×375 | **191.7 px** | **9.3 px** | **6.7 px** | **否** | **否** |

（1280×720 与 667×375 的越界值和独立验收给出的 192.0 / 191.7 一致。）

**根因**

- `#room-panel { flex: 0 0 320px }` 固定 320px，和 canvas 抢宽度；
- `fitCanvas()` 只按 `stage.clientHeight` 定高度、按 16:9 定宽度，**完全不看可用宽度**，也没有居中；
- 字号与患者半径是写死的设计单位，随画布等比缩小，小视口下不可读。

**修正**

- `index.html` 增加 `#stage-view` 包裹层：canvas 只在这一层里做等比 contain，面板是同层 flex 兄弟；
- `style.css` 面板改为 `flex: 0 0 clamp(0px, 26vw, 320px)`（窄屏 30vw），`overflow-x: hidden`，
  头部 `position: sticky`，所以**永远不会超出视口**，关闭按钮也永远在视口内；
- `fitCanvas()` 改为等比 contain：先按可用宽高取最小缩放，再**由取整后的高度反推宽度**，
  宽度不够时以宽度为准——避免整数取整带来的纵向拉伸；
- 可读性下限：`designPx(base, minCss)` 保证标题 ≥ 14 CSS px、正文 ≥ 10.5 CSS px、
  患者半径 ≥ 5.5 CSS px（患者直径 ≥ 11 CSS px），并设 1.9 倍上限避免小视口下文字撑爆房间。

**回归**（同一脚本、同一台 Chromium）

| 视口 | 面板右侧越界 | 标题实测字号 | 患者实测直径 | 关闭按钮 | 购买按钮 | 画布宽高比（目标 1.7778） |
|---|---:|---:|---:|---|---|---:|
| 1280×720 | **0 px** | 16.5 px | 12.0 px | 是 | 是 | 1.7778 |
| 844×390 | **0 px** | **14.0 px** | **11.0 px** | 是 | 是 | 1.7788 |
| 667×375 | **0 px** | **14.0 px** | **10.2 px** | 是 | 是 | 1.7786 |

三点说明，请不要把它读成"已经完美"：

1. 1280×720 下标题从 19.8 px 变成 16.5 px。原因是候选选择**给面板留出真实空间**而不是覆盖在地图上，
   可用宽度从 1280 变成 960。换来的好处是地图右半边的药房/检验室不会被面板盖住。
2. 画布宽高比仍有 ≤ 0.06% 的整数取整误差（修复前 844×390 的 1.7767 反而更歪）。
3. 最小视口 667×375 下患者直径 10.2 px、标题 14 px，**达到设定的下限但不算宽裕**；
   真机在小屏上的实际观感属于"未测"，不能由 CSS 视口仿真推断。
4. 这些都不是换美术能解决的，也不是加系统能解决的——它本来就是布局问题。

### P1-5 · 入口保护与登记容量从未执行

**失败复现**

- `F7.1` 配置 `registration_slots = 4`；
- `F7.3` 5 人同时到达时**峰值同时登记 5 人**，超过上限；
- `F7.4` 实现里根本没有登记位数组；
- `F8.1`/`F8.2` 配置 `admission_gp_wait_budget_seconds = 48`，但 `tick()` 从未引用它。

**修正**

- 新增 `State.regSlots`（长度 = `registration_slots`）与 `State.regQueue`（入口队列，FIFO）；
  患者先走到入口等候位，队首到位后才占用登记位；到位即登记，登记完释放。
- 新增准入等待计量：入口排队 + 首个科室（GP）排队的时间；
  超过 `admission_gp_wait_budget_seconds` 即安全转诊，并计入
  `stats.transferReasons.admission`（与 `patience` / `brokenRoute` 分开计数，便于观察）。

**回归**

- `R9.4`/`R9.5` 8 人压测下峰值同时登记 **4**（用满但不超限）；
- `R9.6` 多出来的患者在入口队列排队；
- `R9.7`/`R9.8` 登记位无泄漏、无患者卡在注册态；
- `R9.9` 8 人全部被处理；
- `R10.2`/`R10.2b` 预算按 tick_hz 换算为 480 tick 且确实被执行；
- `R10.4` 20 人超载时确实触发准入转诊；
- `R10.5` 没有任何仍在 GP 排队的患者超过预算却未被处理；
- `R10.6`/`R10.7` **常规负载下转诊总数为 0**——不会误伤正常玩家。

## 4. 只做必要的可观察性改善：工位与等候位置分离

**改前状态**：`roomCenter()` 让一个房间里所有人都站在房间中心的一个点上；
登记也没有独立位置。扩容在画面上看不出区别。

**改后**

- `slotAnchor(rid, i, slots)`：每个服务位一个独立锚点，并在房间里画出**工位标记**（桌子）。
  未占用/已占用用不同填色，扩容后新增的桌子直接可见。
- `waitAnchor(rid, idx)`：等候位排在房间朝向走廊的一侧，按队位分开，队伍前进时自动重排。
- `regSlotAnchor(i, n)`：登记位按 `registration_slots` 画成一竖排，占用时变色。
- `entryAnchor(idx)`：入口队列位独立。
- 患者落点由"状态"改为"任务"（`pending`）驱动，走到位才切换状态，重排位置不会打断服务。

**证据**

- 单元级：`R11.2`/`R11.3` 2 工位、3 工位锚点互不重合；`R11.4` 等候位互不重合；
  `R11.5` 等候位与工位不在同一行；`R11.6`/`R11.7` 登记位与入口队列位各自独立。
- 行为级：`R11.8`/`R11.9`/`R11.10` 全科扩容到 2 工位后，**同时服务 2 人且落点不同**。
- 画面级：`shots/landscape_*_after_expanded.png`——全科 3 张桌子、药房 2 张桌子，
  第一个工位上有患者在岗；右侧面板显示「当前服务 1 / 3 工位」。（这三张截图为让扩容效果可见，
  用夹具把金币设高后扩容，**不是**正常经济节奏下的截图，特此标注。）
